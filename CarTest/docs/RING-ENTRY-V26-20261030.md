# v26 ring-entry camera candidate

The right-ring diagnostic capture established two independent entry problems.
Observed island-side expansion had the opposite sign to the entry test, so
visible arc rows failed the existing support threshold. After confirmation,
the old route required near observations of the inner boundary although the
island boundary was still visible only farther ahead. Changing the state
counter alone cannot produce an admissible control route.

## Final behavior

Ring-side expansion removes common lateral translation and then measures
rightward expansion for a right ring and leftward expansion for a left ring.
Left/right identities, ordinary steering mapping and controller gains are
unchanged. Arc row/run/span, three-new-frame growth, peak reversal, topology,
calibration and ordinary-route counter-evidence keep their existing thresholds.

A real ENTER-to-INSIDE confirmation opens one entry-transition lease, bounded
by the existing four-second entry time. A current, calibrated far inner arc
and a current near outer boundary anchor a continuous transition through the
reference row. The bridge interpolates geometric centers and applies each
row's frozen calibrated width. Every bridge cell across the full width must
be known road; black/unknown cells, invalid width, missing anchors or bounds
fail closed. Interpolated rows honestly mark both boundaries inferred.
Standard near inner-boundary tracking ends the lease; it cannot restart from
an ordinary route, expired lease or another session.

The main converter requires a certificate tied to the current tracker result,
frame and target buffer. It separately rechecks fresh observed endpoint rows,
their coordinates, contiguous support and span. Mixed observed sides and
double-inferred rows are accepted only under that transition certificate.
Existing locked-side routes retain their original checks. The selected
reference is labeled interpolated rather than reported as an observed edge.
The v26 bundle requires ENTRY_TRANSITION_API_VERSION=1 to reject mixed modules.

Control UART and profile pairing are unchanged. Diagnostic admission reason
names append new values without changing the RNGD3 record layout. The startup
identity is CARTEST_H750_RING_ENTRY_V26_20261030; the small UART diagnostic
identity marker is 0x20261030 and does not verify a complete source package.

## Verification and limits

381 camera tests ran with zero failures/errors and three existing skips. One
additional ground replay is explicitly excluded because its private RAW input
is unavailable. Tests include mirrored transition geometry, masks, endpoint
support, calibration, lease/session lifetime, reference provenance and final
main-loop V3 output. Ordinary routes and false-ring recovery remain covered.
All 23 production modules passed armv7emsp MicroPython cross compilation.

Private captured key poses were additionally evaluated using original row
evidence and masks reconstructed from their raw grayscale images. The new
geometric transition passed the full corridor check and main admission and
produced rightward weighted errors. This is a counterfactual entry-state
geometry check: image sampling does not preserve every threshold-history
update and does not constitute full sensor replay, powered traversal or FPS.

Actual main-loop mirrored synthetic entry packets were checked with the
unmodified H743 parser/servo target mapping. This verifies software direction,
not the physical servo or ground behavior. H743 source/configuration and all
paired ELFs remain unchanged; no H743 reflash/reset or automatic motor start
is part of this change. The previously built fifteen configurations are not
rebuilt for a camera-only change.

The restored H750 native APP is unchanged, SHA256
c693f1ce035f8ff12796e2b21c21d347d5ef8aac7b4a78f6343a089ad45dc154.
Its native build provenance remains the frozen original v25 runtime reference;
the v26 Python candidate uses the same native API and buffer ABI.

v26 is a candidate pending RAM confirmation, powered left/right ground tests
and both preview-off and actual-IDE dynamic 60+ FPS acceptance. v25 stationary

is preserved. The before-change source/configuration and eighteen ELF copies

## v26-r2: ground hand-push evidence and pending-exit correction

The v26-r1 RAM run on the actual H750 captured 129 records and eight original
images with verified transfer checksums. At sequence 1228 the tracker confirmed
INSIDE, selected ring_right and emitted a virtual control error of +230. It
produced 21 valid entry-transition frames. This confirms entry recognition and
software output on this right-ring hand-push sequence; no physical control UART
or powered vehicle traversal was involved.

The same capture contains 19 invalid middle frames with insufficient current
near-boundary evidence. They remain invalid under the existing protection; this
version does not fabricate a route to cover that gap. Later, fresh inner-boundary
tracking returned, but EXIT_CONFIRM cleared the route while waiting for exit
confirmation. v26-r2 rebuilds the current locked inner route during that pending
state using the original calibration, support and corridor checks. Exit proof,
opposite-side exit repair, loss handling and H743 behavior are unchanged.

The lead reviewed the change and its call chain. The final camera suite ran
383 tests with zero failures/errors and three existing skips; the same missing
private RAW fixture is explicitly excluded. Both sides are covered for fresh
pending-exit routes and rejection of missing or blocked evidence. All 23 runtime
modules cross-compiled, and the complete 101-file delivery hash check passed.
The build identity is CARTEST_H750_RING_ENTRY_V26R2_20261030.

The installed camera Python remains v25 until separately authorized deployment.
v26-r2 remains a candidate: its revised pending-exit behavior needs a board

from public checkpoints.

## Host PE7 readout correction

In the retained legacy H743 source, car_pe7_raw_high is assigned at GPIO
initialization, not refreshed in the main loop. It must not be presented as a
current pin measurement. The host read_run_status.ps1 tool now reads the H743
GPIOE IDR register at 0x58021010 through read-only HOTPLUG and reports bit 7
separately from the firmware cached scalar. The JSON retains the raw upload,
register value, read timestamp and the fact that this peripheral read is not
atomic with the firmware snapshots. Dry-run planning includes the same read.

The readout was checked against the project's CMSIS H743 GPIOE layout and on
the connected board at both pin levels. Dry-run output was checked to retain
HOTPLUG and upload-only commands. No H743 source, configuration or ELF changes,
Flash writes, resets, protection bypasses or camera runtime changes are made
by this host correction. Prior cached-high observations alone cannot establish
that the physical switch failed to reach low.

## v26-r3: preserve raw ring observation alongside ordinary counter-evidence

A further right-ring RAM capture reproduced 18 consecutive invalid INSIDE
frames. During those frames an ordinary candidate was accepted, the main loop
skipped the raw single-edge scan, and the selected ordinary rows provided zero
near support to the ring tracker. The retained raw arrays were explicitly not
fresh and are not treated as current measurements. This is a routing/observation
coupling, not evidence that the camera sensor stopped producing images.

For confirmed INSIDE, EXIT_CONFIRM and EXIT_REPAIR states, main now requests a
fresh boundary scan even if the ordinary route is accepted. Its returned
single-edge candidate is observation-only: it does not replace the accepted
ordinary selection or get committed as that route. Profile freshness, session
identity and all normal detector checks still apply.

When both observations are present, the tracker retains the original ordinary
status/edge arrays and near-support summary in fixed buffers, then uses the
fresh raw boundaries for ring geometry and target construction. Ordinary-route
counter-evidence and paired alignment continue to use the separately retained
ordinary observation. Raw rows cannot fill missing near support in an ordinary
route or manufacture the three-frame false-ring recovery condition. Malformed
raw input fails closed; stale arrays are never loaded as a fresh observation.
The observation source is exposed in the tracker result. No entry threshold,
width calibration, mask/corridor check, steering sign, control protocol or H743
code/configuration/ELF is changed.

389 camera tests pass with zero failures/errors and three existing skips;
the same absent private RAW fixture is explicitly excluded. New tests cover
both ring sides, cropped ordinary rows, stale/malformed raw input, independent
ordinary recovery and pending exit. A real main-loop test asserts that accepted
ordinary geometry and a fresh boundary scan reach the tracker together and
checks final mirrored V3 packets. The unchanged host H743 parser/servo mapping
accepts those packets plus ordinary left/straight/right controls. All 23 modules
cross-compile, and the 101-file candidate hash check passes. The build identity
is CARTEST_H750_RING_ENTRY_V26R3_20261030.

v26-r3 is prepared for RAM retest; it is not installed permanently in the camera.
Board ring traversal, powered ordinary/left/right ring behavior and dynamic
60+ FPS including actual IDE preview remain pending. Extra boundary scanning
has a performance cost during confirmed ring states that must be measured on
the H750; previous stationary v25 FPS results are not v26-r3 acceptance.

## v26-r4: ring observation must retain paired boundaries

The v26-r3 RAM retest verified fresh scanning but still rejected an intermediate
entry segment. Inspection found that the single-edge fallback scanner
deliberately excludes an edge when a plausible opposite partner is visible.
Those arrays are suitable for missing-side fallback, not a complete ring
boundary observation. Simply requesting a fresh fallback scan was insufficient.

FastSingleEdgeTracker now exposes observe_ring_boundaries(), guarded by additive
RING_OBSERVATION_API_VERSION=1. It retains paired transitions while running the
same contrast, cache identity, ambiguity, topology and known-road checks. The
ordinary detect() mode still excludes paired transitions exactly as before.
The observation flag is restored in finally, including exceptions. Main uses
this mode once per confirmed-ring frame, independently of ordinary route
validity; it does not promote this candidate to an ordinary fallback route.
The separately retained ordinary counter-evidence introduced in r3 remains.
No turn-sign override, calibration or route-admission relaxation is introduced.

394 camera tests pass with zero failures/errors and three existing skips; the
same unavailable private RAW replay remains explicitly excluded. Paired-mode
tests verify both observed sides, preservation of ordinary fallback behavior,
stale control and dark/unknown rejection, exception cleanup and mixed-API
rejection. All 23 runtime modules cross-compile and the complete delivery hash
check passes. The lead reviewed the main-loop observation/selection separation
and the detector mode lifetime. Build identity:
CARTEST_H750_RING_ENTRY_V26R4_20261030.

The original failed key image was also checked offline using its captured
calibration and historical cache with reconstructed image masks. Paired ring
observation recovers the previously excluded rows; the unchanged full-corridor
check, target certificate and main converter then admit a rightward target.
This is a sampled-image counterfactual with reconstructed mask history, not
full sequence replay, native board validation or powered vehicle acceptance.

v26-r4 is a candidate pending RAM retest, actual ordinary/left/right ring road
tests and dynamic 60+ FPS with actual IDE preview. Permanent camera Python is
still v26-r2 until separately authorized installation. H743 source, PE7 logic,
configuration and paired ELFs remain unchanged throughout r3/r4.

## v26-r5: calibrated single-outer-edge continuation inside the ring

The r4 board retest reduced the intermediate invalid segment but still ended
with unsupported targets. A new still at the retained end pose shows a clear
outer boundary while the inner boundary is outside the view. This still is
not relabeled as the exact final synchronized frame. The tracker previously
required the inner edge throughout INSIDE, leaving no continuation in this pose.

An outer route is now allowed in INSIDE/EXIT_CONFIRM only after main actually
admitted a standard inner-edge ring target in the same session. Merely building
a candidate or selecting the entry interpolation does not establish that
history. Current raw outer rows and the frozen calibrated width feed the
existing locked-edge builder. Additional full-width known-white checks retain
only qualified rows; rejected rows are omitted, never bridged or fabricated.
The retained set must still satisfy near-row count/contiguity and reference
support. A side handoff must stay within 12 doubled-grid-x units of the last
admitted reference center, with history no older than 1500ms. Accepted outer
targets refresh that history; expired outer history does not block an otherwise
fresh, qualified original inner-edge route from reacquiring.

The main converter independently requires a same-result, same-frame, same-buffer,
session/profile and calibration certificate plus fresh raw rows. Observation
side remains explicit in target_side; ring source identity retains the actual
ring direction during outer tracking. No error-sign override or global left/right
swap is used. Diagnostics append outer-continuation admission names without
changing the RNGD3 layout or previous reason indices. The control protocol,
profile pairing, H743 protections, PE7, gains and 200ms/2s loss behavior remain.

402 camera tests pass with zero failures/errors and three existing skips; the
same missing private RAW fixture is excluded explicitly. New tests cover both
directions, main admission and final UART signs, prior-admission requirements,
history expiry, discontinuity, unknown near support, individual rejected rows,
inner reacquisition and session reset. All 23 production modules cross-compile
and the 101-file delivery hashes verify. The lead reviewed history ownership,
certificate lifetime and observation-side/ring-direction separation.

The retained end-pose still was re-scanned offline using historical calibration
and cache and a historical admitted inner reference. Thirty qualified rows
passed the converter and produced positive rightward weighted error. This is a
counterfactual pose check with reconstructed mask history, not synchronized full
replay, native board confirmation or vehicle/FPS acceptance. Build identity is

and dynamic 60+ FPS including actual IDE preview remain pending. Permanent
